### 공통

이전에 CLAUDEmd에 작성을 했었던 글입니다.

```
- 주석 규칙: 주석은 한국어로 작성하되 2줄 이하로 제한한다. (이모티콘 절대 금지)
- Git Commit: 기능 구현이나 버그 수정이 "완전히" 끝났을 때만 자동으로 커밋을 진행하며, 메시지는 한 줄로 간결하게 작성한다.
- 답변 형식 (No Yapping): 인사말과 이모티콘을 생략하고, 다음 3가지만 개조식으로 간결히 출력하라.
  1. 수정한 파일명 (단, 수정 코드가 5줄 이하일 경우에만 해당 코드를 포함)
  2. 무엇을, 왜 수정했는지
  3. 수정 후 예상되는 동작 변화 (또는 확인이 필요한 터미널 검증 명령어)
```

### 여러 세션에서 수정.

만약 Claude에게 시킬 일이 한 프로젝트에 3개 정도 있다고 가정을 하면 일을 시키는 방법은 다양하겠지만 주로 다음과 같을 것입니다.



- 한 세션에서 모두 시키기
- 여러 세션을 만들어서 각각 시키기



**한 세션에서 모두 시키기의 경우**에는 

```
claude야 어디에서 A 적용해주고 어디에서 B 적용해주고 그리고 C 도 적용해줘 ~~~~
```

이런 식으로 한번에 다 말하는 경우입니다.



이 경우 시간도 오래 걸리고 token도 꽤 많이 잡아먹는 것 같습니다.

그리고 질문이 여러개인데 결과물은 다 합쳐서 나오다보니 제가 놓치는 경우가 왕왕 있었습니다.



좋은 점이라고 하면... <mark>코드 충돌은 일어나지 않습니다.</mark>



**여러 세션을 만들어서 각각 시키기**

대화창을 여러개 만든 후 각각 시키는 것입니다.

```
대화창 1 : A 해줘
대화창 2 : B 해줘
대화창 3 : C 해줘
```

이랬을 때는 시간이 매우 단축됩니다.

그리고 결과물도 제가 놓칠 일이 거의 없었습니다. 끝난 순서대로 확인하면 되다보니까..



대신 세션끼리 충돌이 일어날때가 있었습니다.

그러면 답변으로 세션이 끝나면 확인해주세요 라고 하는데...

다시 말해야하나? 싶기도 합니다.



그러니까 수정되어야 하는 부분을 알고 겹치는 것끼리 같이 시켜서 충돌이 일어나지 않게 하는 게 베스트인 것 같습니다.

### 변경 사항 정리

이전 프로젝트에서 느꼈던 불편한 점은 **예전에 말했던 것을 다시 Claude가 고치는 상황** 이였습니다.

Claude와 대화를 하다보면 종종 Claude가 새로운 방향을 추천해주는 경우가 있습니다.

그걸 ok 하면 다음과 같은 상황이 발생합니다.

```
Claude: 이 상황에서는 A보다 B가 더 나을 것 같아요
Me : 오 괜찮은데 그럼 B로 해줘
Claude: 넹 작업 완료~
--------- 몇 일 후 -----------------
Claude: 엥? Claudemd에서는 A가 되어야하는데 현재는 B로 되어있네요. 
git을 보니까 변경된 사항이 있는데 다시 바꿀까요?
```

이런식으로 말하게 됩니다.

물론 그냥 그대로 놔둬 라고 하거나 바로바로 Claudemd를 고치면 되긴 하지만.. 제가 까먹은 상황이면 그게 뭐지? 하면서 작업이 딜레이가 걸려버립니다. 

또는 그냥 지나쳐버리면 아쉽게 되어버릴 때도 있습니다.



이런 것을 방지하기 위해서 현재에는 Rule 관련한 것을 따로 정리를 먼저 했습니다.

```
## 덱과 제시

- 게임 시작 시 덱의 순서가 고정된다
- 덱에서 10장을 손패로 제시한다
- `[확정]` **유저는 손패 중 원하는 것만 배치한다.** 하나도 쓰지 않고 넘겨도 된다
- `[잠정]` **손패는 10장 단위로 통째 교체한다.** 넘기면 남은 카드가 전부 미사용 더미로 가고 새 10장이 제시된다
- 넘긴 도형은 **원래 덱 순서를 유지한 채** 미사용 더미에 보관된다
- 덱이 소진되면 **재구성**한다 — 사용한 도형만 빠지고, **남은 도형은 원래 순서 그대로** 처음부터 다시 제시된다. 섞지 않는다
- `[확정]` **재구성 1회마다 점수가 깎인다.** 많이 넘길수록 덱이 빨리 소진되어 재구성이 잦아진다
- `[잠정]` 재구성 횟수에 상한은 없다. 감점이 억제 역할을 한다
- `[잠정]` **무한 반복 방지** — 재구성 이후 한 바퀴 도는 동안 도형을 **한 장도 배치하지 않고** 다시 재구성에 도달하면 막힘으로 종료한다

```

만약 룰을 고치고 그거에 따른 동작을 바꿔야하는 상황이 있으면 

먼저 룰북을 고치고 Claude에게 내가 이부분 고쳤으니까 확인해서 수정해줘!

라는 식으로 수정을 했습니다.



이렇게 하니 룰은 계속 최신화가 진행되기 때문에 추후에 똑같은 말을 또 할 필요성이 없어졌습니다.

### CSS vs StyledComponent



개인적으로 저는 StyledComponent를 더 좋아합니다.

CSS는 쓰기도 불편하고 보기도 힘들고...

StyledComponent를 사용하면 수정도 쉽고 이해하기도 쉽고



저만 그럴 수도 있어요! :)



AI와 프로젝트를 진행하면 따로 말 안하면 거의 무조건 CSS를 사용하더라구요

그래서 이번에도 수정을 할까 싶었습니다. (앵간하면 무조건..)



**styled 장점**

- 스타일이 컴포넌트 파일 안에 있어 파일 이동이 줄고, 안 쓰는 스타일이 컴포넌트와 같이 삭제됨
- props 기반 조건 스타일(`selected`, `size`, `variant`)이 TS 타입 검사를 받음 — 지금은 className 문자열 조합이라 오타를 컴파일러가 못 잡음
- 클래스명이 자동 해시되어 충돌 걱정 없음
- 테마 객체를 TS로 직접 참조 → `Color.woodDark` 자동완성, 존재하지 않는 키는 컴파일 에러



**styled 단점**

- 런타임 CSS-in-JS
  - 렌더 시 스타일 직렬화·주입 비용. 
  - 보드 셀처럼 다수 요소가 자주 리렌더되는 곳에서 체감될 수 있음 
- 의존성 2개 추가(`@emotion/react`, `@emotion/styled`) + 번들 약 15\~20KB gzip
- React 19 / Vite 8 조합에서 babel 플러그인·SSR 이슈 등 툴체인 마찰 가능성
- 디버깅 시 DevTools에 `css-1a2b3c` 같은 해시 클래스만 보임



CSS를 사용하는 이유.

- 이미 `theme.ts` → CSS 변수 주입으로 styled의 핵심 이점을 확보함. 
- 현재 프로젝트 규모에서 클래스 충돌 문제가 실질적으로 없음.   
필요하면 CSS Modules을 사용. Vite 기본 지원이라 의존성 0으로 해결됨
- 게임 보드는 성능 민감 영역이라 런타임 CSS-in-JS는 오히려 역행
- 얻는 것(props 타입 안전성)보다 잃는 것(의존성, 마이그레이션 비용, 성능 리스크)이 큼



이러한 이유로 그냥 현상 유지 하는 방향으로 결정했씁니다.
