> 책의 목차처럼 데이터 검색 속도를 높이기 위해 사용하는 자료구조입니다.

데이터베이스에 여러 데이터가 쌓이게 되면, 추후 원하는 데이터를 찾기 위해서는 엄청난 수고가 필요합니다.

이때 인덱스를 이용하여 검색으로 빠르게 원하는 정보를 찾을 수 있습니다.

* * *

#### **인덱스의 장점**

1\. 데이터 검색 속도 향상 (SELECT 성능 ↑)

> SELECT \* FROM users WHERE email = 'test@example.com';

-   email에 인덱스가 없으면  
    → users 테이블 전체를 한 줄씩 다 확인 합니다.

-   email에 인덱스가 있으면  
    → 인덱스 트리에서 바로 해당 email 위치를 찾아갑니다.

2\. 정렬 / 범위 조회 속도 향상

> SELECT \* FROM orders  
> WHERE created\_at BETWEEN '2025-01-01' AND '2025-01-31'  
> ORDER BY created\_at;

-   created\_at에 인덱스가 있으면
    -   이미 인덱스가 정렬된 구조라 따로 ORDER BY Sort 과정을  피할 수 있습니다.
    -   범위 검색 + 정렬이 매우 효율적

3\. 유니크 보장

-   내부적으로 Unique Index가 생성됨
-   중복된 email 값이 들어오는 걸 **DB 레벨에서 자동 차단**

> “로그인 ID, 이메일, 주민번호 같은 건 무조건 유니크 인덱스”  
> → 앱 코드에서 체크 + DB 차원에서 이중 방어

#### 인덱스의 단점

1\. 쓰기 성능 저하 (INSERT / UPDATE / DELETE 느려짐)

인덱스가 많을 수록

-   INSERT 할 때  
    → 테이블에 row 추가 + 관련된 모든 인덱스에 엔트리 추가
-   UPDATE 할 때  
    → 기존 인덱스 엔트리 삭제 + 새 엔트리 삽입
-   DELETE 할 때  
    → 인덱스에서도 해당 키 제거

**쓰기가 한 번 일어날 때마다 인덱스 개수 만큼의 부가 작업이 따라오게 됩니다.**

그렇기에 과한 인덱스는 삽입 성능이 크게 떨어질 수 있습니다.

2\. 디스크 / 메모리 사용량 증가

-   인덱스는 **별도의 자료구조(B-Tree, Hash 등)**로 저장됨
-   테이블이 10GB이고,  
    인덱스를 5개, 10개씩 만들면 → 그만큼 추가 디스크 사용

특히,

-   복합 인덱스 (예: INDEX (a, b, c, d, e))는  
    컬럼 개수만큼 인덱스 크기도 커짐
-   메모리에 올릴 수 있는 인덱스 크기가 제한적이면  
    성능에 영향

3\. 유지 보수 / 복잡도 증가

-   어떤 쿼리 때문에 어떤 인덱스를 만들었는지 관리 필요
-   테이블/쿼리 구조가 바뀔 때 인덱스를 같이 수정/삭제해야 할 수도 있음
-   DBA / 개발자 모두 인덱스 전략을 이해하고 있어야 함

* * *

#### **인덱스 구조**

**B-Tree 구조**

> B-Tree는 디스크 / SSD 에 있는 대용량 데이터를 빠르게 찾기 위해 설계된, 가지 수가 많은 균형 이진 검색트리.  
> 항상 균형을 맞춘다는 의미에서 균형트리 (Balanced Tree)라고 불립니다.

![](/images/study-99/1.png)

인덱스는 페이지 단위로 저장되며, 인덱스 키를 바탕으로 항상 정렬된 상태를 유지합니다.

정렬된 인덱스 키를 따라서 리프 노드에 도달하면 인덱스 키, PK 쌍으로 저장되어있습니다.

**B-Tree 핵심 특징**

1\. 한 노드에 **키가 여러 개** 들어간다

-   이진 트리는 노드당 키 1개지만
-   B-Tree는 한 노드에 **여러 키**가 들어감 (예: 50개, 100개 등)
-   그리고 자식도 2개가 아니라, **최대 M개**까지 가질 수 있는 **다진(multi-way) 트리**

비유하자면:

-   BST: “페이지마다 단어 1개 있는 사전”
-   B-Tree: “페이지마다 단어 100개씩 묶어서 있는 사전”

그래서 한 번 노드를 읽으면  
**그 안에서 이진 검색으로 여러 키를 한꺼번에 처리 가능**합니다.

2\. 항상 **균형을 유지하는 트리**

-   삽입/삭제가 일어나도  
    **트리 높이가 크게 깨지지 않도록 자동으로 balance 유지**
-   Red-Black Tree처럼 Self-Balancing Tree의 한 종류지만,  
    **디스크/블록 단위에 최적화**된 구조라고 보면 됨.

3\. 트리의 “높이”가 매우 낮다

노드 하나가 많은 키를 들고 있다 보니:

-   분기 수가 크다 (예: 100갈래, 200갈래)
-   → 같은 데이터 개수일 때 **필요한 높이가 엄청 줄어듦**

예를 들어:

-   이진 트리(분기 2)로 10억 개 관리 → 높이 ≈ 30 정도
-   B-Tree(분기 100)로 10억 개 관리 → 높이 3~4면 충분한 수준

**DB 인덱스 입장에서 “트리 높이 = 디스크 접근 횟수”**  
→ 그래서 B-Tree가 DB에 최적화된 구조인 겁니다.

* * *

인덱스 비트리(Index B-Tree)는 데이터베이스에서 빠른 데이터 검색을 위해 사용하는 균형 잡힌 트리 자료구조로, 하나의 노드에 여러 개의 키(데이터)를 저장하여 디스크 I/O를 줄여 효율성을 높이는 방식이며,

특히 B+트리가 데이터베이스 인덱스로 많이 활용되는데 이는 모든 데이터를 리프 노드(가장 낮은 레벨)에 모아두고 리프 노드들을 연결 리스트로 연결해 범위 검색(Range Search)을 매우 빠르게 처리할 수 있다는 장점 때문입니다. 

**B-Tree (비트리)**

-   특징: 하나의 노드에 여러 개의 키와 자식을 가질 수 있어 트리의 깊이가 얕아짐. 루트부터 리프까지 모든 노드에 데이터가 저장될 수 있음.
-   장점: 이진 트리보다 평균 검색 속도가 빠름.
-   단점: 범위 검색 시 인접하지 않은 노드를 찾으려면 다시 루트부터 탐색해야 하는 비효율이 발생할 수 있음. 

**B+Tree (비플러스 트리)**

1.  특징:
    -   모든 데이터는 리프 노드(Leaf Node)에만 저장되고, 내부 노드(Internal Node)는 탐색 가이드 역할만 함.
    -   리프 노드들이 순차적인 연결 리스트로 연결되어 있어 범위 검색에 최적화.
2.  **장점:** 데이터가 정렬된 순서로 저장되어 범위 검색(예: WHERE age > 20 AND age < 30)이 매우 빠름. 디스크 접근 횟수가 적고 효율적.
3.  **단점:** B-트리에 비해 구조가 복잡해지고, 데이터가 리프에만 있어서 탐색 과정에 약간의 복잡성이 추가될 수 있음. 하지만 전반적인 성능상 이점이 더 큼. 

#### **요약**

데이터베이스 인덱스에서는 B-트리의 장점을 계승하고 단점을 보완한 B+트리가 주로 사용되며, 이는 대규모 데이터 환경에서 효율적인 데이터 접근과 범위 검색 성능을 제공하기 때문입니다.
