코딩을 할 때 중복 코드를 쓰는 경우가 있습니다.

동일한 코드를 하나 이상 앱 프로젝트에 복붙을 하면서 사용을 하다가 버그를 찾아내면 하나하나 고쳐야하는 번거로움이 있습니다.

이 외에도 여러가지 그닥 좋지 않은 이유가 몇몇 있겠지요.

그렇다면 코딩을 할 때 중복 코드를 관리하는 방법으로는 무엇이 있을까요?

중복 코드를 관리하기 위해 swift 정적 라이브러리를 통해 코드를 공유할 수 있습니다.

**정적 라이브러리란?**

정적 라이브러리는 컴파일 된 소스 코드 파일의 모음.

정적 라이브러리를 사용하면 컴파일 하고 모든 파일을 포함하는 단일 파일 안에 래핑할 수 있습니다.

파일의 확장자는 .a입니다.

페이지를 가져와서 책을 만드는 것과 같습니다.

![](/images/ios-78/1.png)

**정적 라이브러리 vs 동적 프레임워크**

iOS 에서 배포를 위해 코드를 그룹화 하는 두 가지 방법을 사용할 수 있습니다.

1.  동적 프레임워크
2.  정적 라이브러리

두가지 방법의 차이점으로는

**동적 프레임워크**는 리소스 ( 예 : 이미지 ) 를 보유할 수 있지만.

**정적 라이브러리**의 경우 리소스를 보유할 수 없습니다.

**동적 프레임워크**는 앱에 느슨하게 연결되어 있고

**정적 라이브러리**는 앱에 하드하게 연결되어 있습니다.

연결을 더 자세히 설명하기 위해 코드 그룹화 메커니즘의 각 유형에 대한 예를 살펴보겠습니다.

**동적 프레임워크 연결**

앱이 코드를 동적으로 사용하면 앱이 실행될 때 코드가 앱과 함께 로드되지 않습니다.

시스템은 앱을 로드하고 앱을 실행하려면 일부 코드를 사용해야한다고 시스템에 알립니다.

시스템은 앱이 의존하는 필요한 코드 청크를 로드합니다.

위 과정은 모두 런타임에 발생합니다.

UIKit가 위 과정의 예입니다.

UIKit는 각 앱에 포함되어 있지 않습니다. 오히려 앱은 실제 코드가 아니라 기능에 필요한 참조와 기능을 가지고 있습니다.

UIKit는 운영 체제에 포함되어있습니다.

로드시 시스템에서 UIKit를 로드합니다.

운영 체제에 포함되지 않는 동적 프레임워크는 어떻게 하나요?

앱과 함께 구축하고 배포하는 프레임워크의 경우

ConsumerApp은 MyDynamicFramework 없이 작동할 수 없습니다.

그렇지 않으면 작동이 중단 됩니다.

따라서 시스템에서 로드해야합니다. 따라서 앱 패키지에 포함되어야합니다.

xcode는 framework라는 앱 패키지 내에 디렉토리를 생성합니다.

프레임워크가 앱의 패키지 프레임워크 디렉토리 또는 시스템 내에 포함되어 있지 않으면 런타임시 앱이 충돌합니다.

**정적** **라이브러리** **연결**

우리 앱이 정적으로 코드를 소비할 때 소비하는 코드는 앱 실행 가능 바이너리에 복사.

![](/images/ios-78/2.png)

시스템이 앱을 로드하면 정적 라이브러리 기능이 단일 실행 파일로 로드 됩니다.

**왜 정적 라이브러리를 사용하는 가?**

동적 프레임워크와 유사한 정적 라이브러리를 사용하는 몇가지 이유.

-   코드 재사용성
-   앱과 관련 없는 코드 숨기기 ( 비공개 및 내부 액세스 사용 )

정적 라이브러리와 동적 프레임워크 모두에 대해 컴파일된 형식만 배포하는 경우.

-   비밀 코드 공유를 피하고 기능만 배포
-   앱 컴파일 시간 단축

하지만 동적 프레임워크 대신 정적 라이브러리를 사용하는 이유?

**정적 라이브러리가 있는 앱은 동적 프레임워크가 있는 앱보다 빠르게 로드됩니다.**

동적 프레임워크는 런타임시 메모리에 느리게 로드되고 여러 프로세스와 공유할 수 있다는 장점이 있습니다.

동적 프레임워크가 ios의 여러 앱에서 사용되는 경우 훌룡하게 작동됩니다.

iOS 시스템 동적 프레임 워크는 여러 앱에서 사용되며 앱이 시작되기 전에 로드될 가능성이 높으므로 앱 시작 시간이 절약 됩니다.

그러나 앱에 포함된 동적 프레임워크의 경우 시작시간이 훨씬 느려질 수 있습니다.

( 운영 체제가 아니라 앱 내부에 포함된 프레임워크 )
