지뢰찾기 아레나에서 제일 늦게 붙은 모드입니다. 이름은 너에게 닿기를입니다.

80×80 보드에 두 사람이 서로 멀리 떨어져 놓입니다.

상대가 어디 있는지도 모르고, 자기 주변 세 칸 너머는 구름에 가려 안 보입니다.

각자 길을 뚫다가 둘이 연 칸이 맞닿으면 그 순간 둘 다 성공입니다.

걸린 시간이 협동 랭킹에 올라갑니다.

승패가 없는 모드를 만든 건 이게 처음이었습니다.

## 만남은 상하좌우로만 인정합니다

이 모드는 승리 판정이 곧 게임입니다.

그런데 만났다는 걸 정의하는 게 생각보다 어려웠습니다.

기획 노트에도 이 질문이 그대로 남아 있습니다.

> 만남: 빈칸이라 하면 주변에 지뢰가 없는 0인 상태를 말하는 건가요? (…) 아직 안 열린 cell을 말하는 거라면 포함시키면 안 됩니다.

결국 두 사람이 각각 연 안전 칸이 상하좌우로 붙으면 만남으로 정했습니다.

```swift
private static let neighbors4 = [(-1,0),(1,0),(0,-1),(0,1)]

private func checkMeet(_ r: Int, _ c: Int) -> Bool {
    let cell = grid[r][c]
    guard cell.isRevealed, !cell.exploded, let owner = cell.owner else { return false }
    let other: FlagOwner = (owner == .me) ? .opponent : .me
    for (dr, dc) in Self.neighbors4 {
        ...
        if n.isRevealed, !n.exploded, n.owner == other { return true }
    }
    return false
}
```

8방향이 아니라 4방향인 게 핵심입니다.

대각선으로 붙는 걸 만남으로 치면, 두 칸 사이의 대각 자리에 지뢰가 끼어 있어도 만난 게 됩니다.

길이 이어지지 않았는데 이어졌다고 하는 셈입니다.

4방향은 두 칸 사이에 낄 칸이 아예 없습니다. 그래서 중간에 지뢰가 끼면 안 된다는 규칙을 판정식에 안 넣고도 지켜집니다.

터진 칸은 양쪽에서 다 제외합니다.

지뢰를 밟아서 드러난 자리는 지나갈 수 있는 길이 아닙니다.

## 시작점은 30칸 이상 떨어뜨렸습니다

시작점 둘은 시드에서 뽑습니다. 조건은 체비셰프 거리 30 이상입니다.

```swift
let minSeparation = 30          // 두 시작점은 최소 이만큼 떨어진다

private func pickStarts<G: RandomNumberGenerator>(using rng: inout G) -> ((Int, Int), (Int, Int)) {
    ...
    for _ in 0..<200 {
        a = (Int.random(in: m..<size - m, using: &rng), ...)
        b = (Int.random(in: m..<size - m, using: &rng), ...)
        if max(abs(a.0 - b.0), abs(a.1 - b.1)) >= minSeparation { return (a, b) }
    }
    return (a, b)   // 폴백(이론상 도달 안 함)
}
```

같은 시드에서 같은 순서로 뽑기 때문에 양쪽이 같은 두 점을 얻습니다.

그리고 호스트가 A, 게스트가 B에서 시작합니다.

서버가 좌표를 내려보내지 않아도 되고, 상대가 어디서 출발했는지도 각자 계산해서 압니다.

여기도 보물찾기처럼 두 시작점을 잇는 안전 통로를 먼저 팝니다.

18% 확률로 뿌리는 지뢰가 운 나쁘게 벽을 만들면 아무리 잘해도 못 만나는 판이 나옵니다.

그건 협동 모드에서 제일 나쁜 결말입니다. 길은 안 보이지만 반드시 있습니다.

## 안개가 상대를 알려 줍니다

내가 연 칸을 기준으로 세 칸까지만 보입니다. 그 밖은 구름입니다.

```swift
let fogRadius = 3               // 내가 연 칸 기준 이 거리(체비셰프)까지 보인다
```

![협동 시뮬 — 호스트 시작 (64,71), 게스트 시작 (41,25), 46칸 떨어짐. 연푸른 칸이 안개입니다](/images/mineapp-touch-coop/sim-start.png)

연푸른 칸이 아직 안 걷힌 안개입니다. 한 번 걷힌 곳은 계속 보입니다.

안개는 시야를 좁히는 장치이면서 동시에 신호 장치입니다.

상대가 연 칸이나 상대 깃발이 내 안개 안에 들어오면 그게 화면에 나타납니다.

아무것도 없던 자리에 갑자기 숫자나 깃발이 보이면, 저쪽에서 누가 오고 있다는 뜻입니다.

진행바나 화살표로 알려 주는 대신, 판을 보다가 알아채게 했습니다.

가운데 확성기 아이콘이 보이는데, 보드에 다섯 개 박혀 있는 칸입니다.

거기 도달하면 파트너 화면에 여기서 울렸다는 방향 화살표가 잠깐 뜹니다.

안개 안에서 서로를 못 찾고 헤매는 시간이 길어질 때, 큰 방향이라도 맞추라고 넣었습니다.

## 지뢰를 밟으면 파트너가 손해를 봅니다

여기가 협동 모드다운 부분입니다.

밟은 사람은 1.5초 멈추고, 파트너의 깃발 하나가 무작위로 떨어집니다.

```swift
/// 파트너가 지뢰를 밟아 내 깃발 1개가 무작위로 떨어진다(닫힌 칸 복귀 + 동기화 해제).
func dropRandomFlag() {
    var flagged: [(Int, Int)] = []
    ...
    guard let pick = flagged.randomElement() else { return }
    grid[pick.0][pick.1].isFlagged = false
    onPushFlag?(pick.0 * size + pick.1, false)
}
```

내 실수가 나한테만 돌아오면 협동이 아니라 그냥 각자 하는 게임입니다.

벌이 파트너에게 가야 상대가 뭘 하고 있는지 신경 쓰게 됩니다.

어느 깃발이 떨어졌는지는 알려주지 않습니다. 그래서 파트너가 밟은 걸 알면 자기 표시를 한 번 훑어보게 됩니다.

깃발이 파트너에게 동기화되는 것도 이 모드만의 규칙입니다.

대전에서 깃발은 점수 표시인데, 여기서는 여기 지뢰가 있다는 메모입니다.

안개 너머에서 파트너의 깃발이 보이면 그것만으로 도움이 됩니다.

## 혼자 확인할 수 있는 시뮬을 만들었습니다

이 모드를 만들면서 제일 곤란했던 건 확인이었습니다.

두 사람이 필요한 기능인데, 폰 두 대로 매칭을 잡아 가며 시작점 거리나 만남 판정을 고치는 건 못 할 짓이었습니다.

그래서 한 기기에서 호스트와 게스트를 동시에 띄우는 시뮬을 따로 만들었습니다.

실행 인자에 `--touchsim` 을 주면 이 화면으로 바로 뜹니다.

```swift
final class TouchCoopSim: ObservableObject {
    let host = TouchModel(size: 80)
    let guest = TouchModel(size: 80)
    ...
}
```

중요한 건 실제 모델을 그대로 쓴다는 것입니다.

검증용으로 따로 만든 가짜 로직이 아니라, 진짜 `TouchModel` 두 개를 인메모리 루프백으로 이었습니다.

한쪽이 연 칸이 상대 보드에 상대 색으로 들어가는 모양이 Firebase 동기화와 같습니다.

그래서 여기서 통과하면 온라인에서도 대체로 맞습니다.

화면 위에는 매번 확인해야 하는 것들을 판정으로 띄웠습니다.

서로 다른 곳에서 시작했는지, 몇 칸 떨어졌는지, 양쪽이 같은 보드를 보고 있는지를 봅니다.

호스트가 아는 상대 시작점이 게스트의 실제 시작점과 같은지도 봅니다.

이 마지막 항목이 실제로 값을 했습니다. 두 시작점을 뒤바꿔 배정하는 실수는 한쪽 화면만 봐서는 절대 안 보입니다.

자동으로 만나기를 누르면 양쪽이 상대 시작점 쪽으로 열 수 있는 칸을 골라 파 들어갑니다.

같은 시드, 같은 판인데 시점을 바꾸면 보이는 게 완전히 다릅니다.

협동 모드에서 상대가 지금 뭘 보고 있는지 개발자가 확인할 방법이 이것뿐이었습니다.

## 정리

판정을 좁히면 규칙이 줄어듭니다.

만남을 4방향으로 정한 덕분에 사이에 지뢰가 끼면 안 된다는 규칙을 따로 안 썼습니다.

8방향으로 뒀다면 그 예외를 코드에 적고, 그다음에는 대각 두 칸이 다 지뢰면 어떻게 할지를 또 정하고 있었을 겁니다.

둘이 필요한 기능은 혼자 확인할 방법부터 만드는 게 빨랐습니다.

시뮬을 먼저 만들 걸 그랬다고 생각합니다.

폰 두 대로 확인하던 며칠 동안 고친 것보다, 시뮬을 붙이고 한 시간 동안 고친 게 더 많았습니다.
