## ShapeSpider 세팅

### 어떤 것을 사용할 것인지?

우선 웹 게임으로 만들 예정입니다.

Native 앱으로 하기에는 화면에 부담이 좀 있을 것 같았습니다.  
또한 빠르게 만들어보기에는 웹이 더 나을 듯 했기 때문입니다.



해당 게임이 주기적인 업데이트가 필요한 게임으로 보여지지 않았습니다.

우선 웹으로 하고 추후에 native로 감싸서 만들어도 충분할 것으로 보였습니다.

#### 렌더링 방식


| 방식             | 장점                                                                                   | 단점                                  |
| -------------- | ------------------------------------------------------------------------------------ | ----------------------------------- |
| DOM + CSS Grid | 100개의 셀 정도는 성능에 문제가 없습니다.<br>반투명 프리뷰 붉은 경고 등등 여러가지를 css로 처리가 가능합니다.<br>디버깅이 정말 빠릅니다. | 파티클, 수백 개 오브젝트 애니메이션에는 부적합합니다.      |
| Canvas 2D      | 자유로운 연출, 대량 오브젝트                                                                     | 히트 테스트, 드래그, 레이아웃, 반응형을 직접 구현해야합니다. |




> 저희 게임에는 엄청나게 많은 오브젝트가 있는 것도 아니고 격자 UI 앱에 가깝습니다.  
> 테트리스류를 Canvas로 만드는 것이 대중적이지만 위 게임은 낙하같은 애니메이션도 필요없고 오히려 카드를 놓는 느낌이 더 알맞습니다.



#### 프레임워크 비교




| 스택                    | 장점                                                                                           | 단점                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **Vite + React + TS** | 순수 클라이언트 SPA에 최적, 빌드/HMR 빠름. 드래그 라이브러리(dnd-kit), 상태관리, 테스트 생태계가 압도적으로 두꺼움. 정보 검색 시 사례가 가장 많음 | React 리렌더 최적화를 조금 신경 써야 함                                                                       |
| **Next.js**           | SEO, 라우팅, API Routes(나중에 랭킹 서버), Vercel 배포 매끄러움.                                             | 게임은 100% 클라이언트라 SSR 이점이 없음. `'use client'`, hydration, 서버/클라이언트 경계 같은 **쓰지도 않을 복잡도**를 계속 의식해야 함 |
| **Vue 3 + Vite**      | 반응성 모델이 직관적, SFC가 깔끔. 익숙하다면 생산성 최고                                                           | dnd-kit급 드래그 라이브러리가 없음 → 직접 구현 비중↑. 게임 관련 레퍼런스가 React보다 적음                                      |
| **Svelte + Vite**     | 번들 가장 작고 코드 간결, 런타임 오버헤드 없음                                                                  | 생태계가 가장 얇음. 드래그·애니메이션 대부분 자작                                                                    |
| **바닐라 TS + Vite**     | 의존성 0, 완전한 제어                                                                                | 보드/트레이/수집함/모달의 상태 동기화를 손으로 관리 → 기능 늘수록 급격히 힘들어짐                                                 |




Next를 사용하는 합리적인 이유는 저희 블로그에 게임 페이지를 통합하고 싶을 때 뿐입니다. 그 외에는 크게 이득이 없다고 보여집니다.  
그리고 Vite로 만들어도 못할것도 없습니다.

### Claude.md



저는 이 친구가 토큰과 답변의 퀄리티에 큰 영향을 미친다고 생각했습니다.

```text
# Shape Spider

2D 공간 전략 퍼즐 (폴리오미노 + 스파이더 카드게임). 클라이언트 전용 SPA.
Game Rules: `docs/GAME_RULES.md` 참조
데이터 모델과 설계: `docs/GAME_DESIGN.md` 참조

## STACK & Cmd

- Vite 8, React 19, TypeScript, oxlint
- `npm run dev` | `npm run build` | `npm run lint`

## Architecture Constraints (STRICT)

- 순수 Core: `src/core/` 내부 코드는 순수 TypeScript로만 작성하며 `React` 관련 임포트를 절대 금지한다.
- 1차원 보드: 보드는 1차원 배열로 모델링한다 (`index = r * cols + c`). 도형 단위로 관리하지 마라.
  - `type Cell = { color: ColorId; pieceId: PieceId } | null;`
- 목적지 기반 선택 규칙: 추출 선택 로직은 목적지가 결정하며, `(board, startCell, dest) -> Coord[]` 형태로 분리한다.
- DOM 렌더링: Canvas 및 외부 게임 엔진 사용을 금지한다. DOM + CSS Grid만 사용하고, 이동 시 셀 리렌더링을 피하라. (선택 프레임은 오버레이 `div` 1개로 처리)
- 입력 처리: HTML5 Drag & Drop API 사용을 금지한다. Pointer Events를 사용하고, 보드 컨테이너에 `touch-action: none`을 필수로 지정하라.

## Coding Conventions & Agent Rules

- 불변성 유지: 상태는 불변(Immutable) 객체로 다루고, 핵심 함수는 새 객체를 반환한다.
- 매직 넘버 금지: 모든 설정값은 `GameConfig`를 참조한다.
- 주석 규칙: 주석은 한국어로 작성하되 2줄 이하로 제한한다. (이모티콘 절대 금지)
- Git Commit: 기능 구현이나 버그 수정이 "완전히" 끝났을 때만 자동으로 커밋을 진행하며, 메시지는 한 줄로 간결하게 작성한다.
- 답변 형식 (No Yapping): 인사말과 이모티콘을 생략하고, 다음 3가지만 개조식으로 간결히 출력하라.
  1. 수정한 파일명 (단, 수정 코드가 5줄 이하일 경우에만 해당 코드를 포함)
  2. 무엇을, 왜 수정했는지
  3. 수정 후 예상되는 동작 변화 (또는 확인이 필요한 터미널 검증 명령어)
- 개발 중 룰 자체가 수정이 되는 경우 `docs/GAME_RULES.md` 수정 요청.

```



- 기술 및 환경 컨텍스트 주입
  - AI가 갑자기 엉뚱한 빌드 도구나 옛날 버전의 문법을 사용하는 것을 막기위해 `Vite8` 이나 `React19` 같은 현재 프로젝트 환경에 딱 맞는 코드를 작성하도록 기준을 잡아줬습니다.
  - 스스로 테스트나 린트를 돌려볼 수 있는 기본 명령어도 전달해주는 역할을 합니다.
- 설계 탈선 및 할루시네이션 차단
  - AI는 보통 가장 흔한 패턴 (ex. 2D 게임 = Canvas 사용. 2차원 배열)을 무비판적으로 따르려는 경향이 있습니다
  - `React 의존성 0, 1차원 보드, DOM+CSS Grid 사용`을 강제하므로써 AI가 마음대로 구조를 뒤엎거나 외부 라이브러리를 끌고 오는 것을 차단했습니다.
- 코드 품질 및 일관성 유지
  - 불변성 유지, 매직 넘버 금지 등의 규칙을 통해 여러 번 대화를 나누고 기능이 추가되어도 코드 스타일이 파편화되지 않게 돕습니다. 사람이 읽고 유지보수하기 좋은 고품질 코드를 일관되게 생성하도록 강제하는 장치입니다.
- 비용 절감 및 워크 플로우 자동화
  - 비용 방어**:** 인사말, 이모티콘, 불필요한 파일 전체 출력을 막고 핵심만 요약하게 하여, 요금이 가장 비싼 출력 토큰 비용을 극적으로 낮춥니다.
  - 형상 관리**:** 기능이 완성될 때만 깔끔한 한 줄 커밋을 남기게 하여 Git 히스토리가 쓰레기통이 되는 것을 방지합니다.
  - 문서 동기화**:** 기획과 구현이 달라질 때 AI가 스스로 문서를 업데이트하게 만들어, 기획서가 실제 코드와 안 맞는 문서가 되는 것을 예방합니다.
