### Swift에서 Final 이란?

( 실제로 sdk개발할 때 내가 사용했었는데... 바보냐 너.. )

> final이 붙은 클래스 / 메서드는 더이상 상속하거나 override 하지 않는 다는 의미의 키워드

-   상속 불가
-   override 불가

```swift
class BaseViewController: UIViewController {
    func setupUI() {
        // 서브클래스에서 커스터마이징 가능
    }
}

final class MyViewController: BaseViewController {
    // 이 클래스는 더 이상 상속할 수 없음
    
    final override func setupUI() {
        // 여기까지는 override 가능하지만
        // 이제 이 메서드도 하위 클래스에서 override 불가
    }
}
```

**final을 사용하는 이유**

1\. 설계 의도 명확화

해당 타입은 상속을 전제로 설계 되지 않았다는 것을 바로 보여줄 수 있습니다.

상속 이나 오버라이드를 하게 되면 위험하다는 의도로 코드를 표현합니다.

**라이브러리 / SDK를 만들 때 특히 중요합니다. ( 에휴,,, 이딴게 3년 동안 sdk 만든 놈? )**

2\. 성능 최적화

final이면 컴파일러가 이던 동적 디스패치를 하지 않아도 된다고 확신이 가능합니다.

그렇기에 런타임에서 굳이 final은 확인을 하지 않아도 됩니다.

결과적으로 inlining, devirtualization 같은 최적화를 세게 걸 수 있습니다.

**언제 써야할까요?**

-   ViewModel, Manager 같은 **상속할 이유가 없는 클래스**에 기본으로 final 붙이기
-   UIKit/SwiftUI에서 특정 ViewController나 View를  
    라이브러리처럼 제공하고 싶을 때
-   내부 구현을 건들지 못하게 막고 싶은 핵심 로직

### UIKit에서 frame를 작성을 할때 그 frame에 넣는 width와 height값은 뭔가요?

**Frame이란**

> UIView의 슈퍼뷰(부모 뷰)의 좌표계에서 본 이 뷰의 위치(x, y)와 크기(width, height)

```swift
view.frame = CGRect(x: 50, y: 100, width: 200, height: 100)
```

-   x, y : 슈퍼뷰 기준 왼쪽 위 위치
-   width, height : 이 뷰의 너비 / 높이

**단위**

> frame의 단위는 픽셀(px)이 아니라 포인트(pt) 입니다.

-   iOS는 논리 좌표계로 포인트를 사용합니다.
-   실제 디바이스는 scale에 따라 px 수가 달라집니다.

```swift
view.frame = CGRect(x: 0, y: 0, width: 100, height: 50)
```

-   논리 크기: 100pt × 50pt
-   iPhone 15 Pro는 scale 3이므로:
    -   실제 픽셀 기준: 300px × 150px 정도에 해당

#### frame vs bounds 간단 비교

-   frame : **슈퍼뷰 기준** 위치/크기
-   bounds : **자기 자신 기준** 위치/크기 (보통 (0,0,width,height))

오토레이아웃 많이 쓰더라도,  
여전히 커스텀 레이아웃, 애니메이션, 터치 영역 조정할 때  
frame을 직접 다뤄야 할 때가 많습니다.

### 현재 사용하고 있는 기기의 해상도는?

이 부분이 정말 부끄러웠습니다.

iOS 개발 하겠다는 사람이 자기 기기의 해상도는 알아야하는 거 아닌가?

#### 픽셀 해상도 & 스케일

애플 공식 스펙 기준:

-   **물리 해상도(픽셀)**:  
    **2556 × 1179 px**, 약 460 ppi
-   **논리 해상도(포인트)**:  
    **393 × 852 pt**, **scale = 3**

즉,

> **1pt = 3px** (가로/세로 모두)

#### 개발할 때 어떻게 쓰이나?

```swift
print(UIScreen.main.bounds) // 대략 (0,0,393,852) pt
```

-   오토레이아웃, frame, constraints 등은 전부 **pt 기준**으로 생각
-   실제 픽셀 수는 시스템이 알아서 scale을 곱해서 처리

let view \= UIView(frame: CGRect(x: 0, y: 0, width: 100, height: 100))

> 논리 좌표: 100pt × 100pt

-   실제 표시: 300px × 300px (3x 디스플레이)

> 아이폰 15 Pro는 2556×1179의 3배율 디스플레이라,  
> 개발자는 393×852pt 기준으로 레이아웃을 잡고,  
> 실제 픽셀 수는 시스템이 알아서 처리해줍니다.

### Segmentation Fault / Segmentation Crash란?

> 프로세스가 접근하면 안 되는 메모리 영역에 접근했을 때 OS가 내리는 강제 종료 신호(에러) 입니다.

-   OS는 각 프로세스에게 자기가 써도 되는 주소 범위만 허용해 줌
-   그 범위를 벗어난 주소에
    -   읽기(Read)
    -   쓰기(Write)
    -   실행(Execute)  
        를 시도하면 → **Segmentation Fault** 발생 → 프로세스 종료

POSIX 환경에서는 SIGSEGV 시그널로 알려져서,

콘솔에 Segmentation fault: 11 같은 메시지가 찍히는 경우가 많습니다.

C에서 제일 많이 보고, Swift/iOS에서는 주로 EXC\_BAD\_ACCESS 형태로 보입니다.

#### Swift에서는

-   옵셔널, 범위 체크, ARC, 안전한 컬렉션 등을 통해  
    이런 류의 버그를 **대부분 런타임 에러나 컴파일 에러로 막아줍니다.**

그래도 다음과 같은 경우

-   UnsafePointer, UnsafeMutablePointer 등을 잘못 사용할 때
-   C/ObjC 라이브러리와 연동하면서 포인터를 잘못 넘길 때
-   컴파일러 내부 버그가 있을 때

여전히 **세그멘테이션 크래시**를 볼 수 있습니다.

> 허용되지 않는 메모리 영역을 건드려서 OS한테 맞고 죽었다

### 1px에 몇 바이트?

> 픽셀(px)은 화면/이미지에서 색을 표현하는 “점 하나”입니다.

이 점 하나를 메모리에 저장할 때:

-   이 픽셀의 **색상 정보를 몇 비트(몇 바이트)로 표현하냐**에 따라  
    필요한 바이트 수가 달라집니다.  
    (이걸 컬러 포맷, 색 깊이라고 부름)

### 대표적인 포맷과 바이트 수

1.  **8bit 그레이스케일**
    -   밝기만 0~255(1바이트)로 저장
    -   **1픽셀 = 1바이트**
2.  **24bit RGB**
    -   R, G, B 각 채널 8bit (1바이트)씩
    -   총 24bit = 3바이트
    -   **1픽셀 = 3바이트 (RGB)**
3.  **32bit RGBA**
    -   R, G, B, A 각 8bit
    -   총 32bit = 4바이트
    -   **1픽셀 = 4바이트 (RGBA)**

iOS에서 스크린/이미지 처리를 할 때는 보통  
**32bit RGBA (또는 BGRA)** 포맷을 많이 쓰기 때문에

> **실무에서는 1px = 4바이트인 경우가 대부분입니다.**

### 메모리 사용량 계산 예시

예를 들어, iPhone 15 Pro 해상도 전체 화면을  
32bit RGBA 이미지로 캡처한다고 하면:

-   해상도: 2556 × 1179 px
-   픽셀 수: 2556 × 1179 ≈ 약 3,013,000 px
-   1px = 4바이트라고 가정하면:

> 대략 3,013,000 × 4 ≒ **12MB 정도**
