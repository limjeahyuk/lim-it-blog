## Redirect &amp; Rewrite

> 웹 개발에서 트래픽을 제어하는 핵심 기술 입니다.  
> 브라우저의 URL 변경 여부와 동작 방식에서 명확한 차이가 있습니다.



제가 작업을 하다가 프로젝트를 두개를 만들었습니다.

별개의 프로젝트로 작업을 하던 도중, 하나의 프로젝트 도메인 뒤에 `/blog` 와 같은 것을 통해서 합쳐야 하는 상황이 왔습니다.

제 머리 속으로는 그러면 한 프로젝트로 합쳐야하나? 라는 생각이 들었습니다.

그런데 너무 별개의 프로젝트였기에 답이 안나오던 상황에 리라이트 라는 것을 알게 되었습니다.



그러면서 리다이렉트와 리라이트에 대해 공부하게 되었습니다.




| 구분             | 리다이렉트 (Redirect)                           | 리라이트 (Rewrite)                             |
| -------------- | ------------------------------------------ | ------------------------------------------ |
| **URL 주소창**    | **변경됨** (사용자가 인지함)                         | **변경 안 됨** (사용자는 알 수 없음)                   |
| **동작 주체**      | 브라우저<br>(서버의 명령을 받아 새 URL로 재요청)            | 서버<br>(내부적으로 다른 경로의 리소스를 매핑하여 반환)          |
| **응답 속도**      | 추가적인 네트워크 왕복이 발생하여 상대적으로 느림                | 클라이언트의 추가 요청이 없어 빠름                        |
| **HTTP 상태 코드** | 주로 301(영구 이동), 302/307(임시 이동) 반환           | 일반적으로 200(성공) 반환                           |
| **SEO 영향**     | 301 사용 시 기존 URL의 검색 순위(랭킹)를 새 URL로 온전히 이전함 | 동일한 콘텐츠가 여러 URL로 노출될 수 있어 중복 콘텐츠 패널티 주의 필요 |




### 리다이렉트

> 브라우저가 주도하여 재요청합니다.



리다이렉트는 서버가 브라우저에게 새 주소로 다시 요청해달라고 지시하는 과정입니다.

네트워크 통신이 두번 발생하여 사용자 입장에서는 화면이 잠깐 멈춘 뒤 주소가 바뀌는 것을 경험하게 됩니다.



#### 동작 흐름

- 요청 : 브라우저가 서버로 A 주소를 요청합니다.
- 지시 : 서버는 리소스가 이동했음을 알리고, 리다이렉트 상태 코드와 새 주소 B 를 반환합니다.
- 재요청 : 브라우저는 주소창을 B로 변경하고 서버에 B를 다시 요청합니다.
- 최종 응답 : 서버가 B의 내용을 브라우저에 전달합니다.



#### 장단점

- 장점 : 사용자가 새로운 URL을 북마크하거나 공유할 수 있습니다.  
301 리다이렉트를 통해 기존 페이지의 검색 엔진 최적화 점수를 안전하게 새 주소로 넘길 수 있습니다.
- 단점 : 클라이언트가 서버에 요청을 한 번 더 보내야 하므로 로딩 시간이 미세하게 길어집니다.
- 주요 사용처:
  - 도메인 이름을 변경했을 때
  - HTTP 접속을 HTTPS로 강제 전환할 때
  - 삭제되거나 이동된 페이지의 트래픽을 새 페이지로 유도할 때
  - 폼 제출 후 중복 제출을 막기 위해 다른 페이지로 이동시킬 때



### 리라이트

> 서버 내부의 경로 매핑



리라이트는 브라우저의 추가 통신 없이 서버 내부에서만 사용자가 요청한 겉보기 주소를 실제 시스템 파일 경로나 파라미터로 변환하여 처리하는 과정입니다.



#### 동작 흐름

- 요청 : 브라우저가 서버에 A 주소를 요청합니다.
- 내부 변환 : 웹 서버가 미리 설정된 규칙을 확인하고, 이를 실제 백엔드가 이해하는 경로인 /B로 몰래 치환합니다.
- 로직 실행 : 치환된 실제 경로에서 데이터베이스 조회 등의 서버 작업을 수행합니다.
- 최종 응답 : 서버는 주소 변경 없이 200(성공) 코드와 함께 결과물을 브라우저로 보냅니다.  
브라우저 주소창은 여전히 A 로 유지되지만 화면은 변경되었습니다.

#### 장단점

- 장점 : 네트워크 추가 요청이 없어서 빠릅니다.  
서버 내부의 복잡한 파일 경로나 구조를 사용자에게 숨길 수 있어 보안과 깔끔한 URL 유지에 유리합니다.
- 단점 : 주소창의 URL과 실제 불러오는 리소스 경로가 달라 디버깅이 까다로울 수 있습니다.
- 주요 사용처 :
  - 복잡한 동적 URL을 깔끔하게 만뜰 때  
  예) `/product.php?id=123`  =&gt; `/product/123` 
  - SPA에서 모든 라우팅 요청을 index.html 하나로 보낼 때
  - A/B 테스트 시 같은 URL 에서 사용자 그룹에 따라 다른 페이지를 보여줄 때

### 리라이트가 빠르고 더 좋은 거 아닌가요?

리라이트가 추가적인 네트워크 요청을 발생시키지 않고 사용자에게 깔끔한 화면을 제공하므로 성능상 유리해 보이는 것은 사실입니다. 하지만 두 기술은 경쟁 관계가 아니라 **완전히 다른 목적을 가진 도구**입니다.

특정 상황에서는 리다이렉트를 쓰지 않으면 치명적인 시스템 오류나 비즈니스 손실이 발생합니다.



**리다이렉트가 반드시 필요한 순간**

- 중복 결제 및 데이터 제출 방지 ( PRG 패턴 )  
사용자가 쇼핑몰에서 결제를 완료한 직후 브라우저의 새로고침을 누르면 동일한 결제 요청이 서버로 다시 전송될 위험이 있습니다.  
이때, 서버가 완료 페이지로 리다이렉트를 강제하면, 새로고침을 하더라도 결제가 중복으로 일어나지 않습니다.
- 브랜드 이전 및 도메인 교체  
도메인을 A에서 B로 교체를 했을때 리다이렉트를 사용하지 않으면 사용자는 A에서 계속 머물게 됩니다.  
사용자가 바뀐 도메인을 인지하도록 할 필요가 있습니다.
- SEO 보존  
구글 검색 1위에 노출되던 페이지의 카테고리를 개편하여 주소가 변경되었을 때, 301 리다이렉트를 걸어주지 않으면 검색엔진은 새 주소를 트래픽이 0인 신규 문서로 취급합니다.  
리다이렉트는 검색 엔진에게 기존 페이지가 쌓아온 신뢰도와 권위를 새 주소로 넘기겠다는 양도 증서 역할을 합니다.



**리라이트가 반드시 필요한 순간**

- 보안 강화 및 구조 은닉  
`/board.php?type=notice&id=405` 같이 내부 시스템 구조와 데이터베이스 키값이 그대로 노출되는 주소를 `/notice/405`로 변환하여 사용자에게 제공할 때 압도적으로 유리합니다.
- **마이크로서비스 통신 (리버스 프록시)**  
사용자는 `api.mysite.com` 하나로만 접속하지만, 서버 내부적으로 리라이트를 거쳐 결제 서버, 이미지 서버, 채팅 서버 등 물리적으로 분리된 여러 백엔드로 트래픽을 사용자 모르게 분배할 수 있습니다.
