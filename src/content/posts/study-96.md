> 컴퓨터가 가지고 있는 실제 물리적 메모리 RAM 의 크기에 관계없이,  
> 프로그램이 사용할 수 있는 메모리 공간을 확장하는 기술.

* * *

#### Virtual Memory 가 필요한 이유

컴퓨터의 메모리는 제한적입니다.

그런데 컴퓨터에 여러 프로그램을 왕창 사용을 하게 되면 RAM을 넘어서게 될 수도 있습니다.

이때 자주 쓰는 부분만 RAM으로 두고 나머지는 디스크에 잠시 빼 두었다가 필요할 때 다시 가져오는 방식으로 사용합니다.

프로세스 전체가 메모리에 올라오지 않더라도 실행이 가능하도록 하는 기법입니다.

물리 메모리가 항상 충분하지 않으니까

-   RAM이 8GB인데,  
    여러 프로그램이 합쳐서 12GB 정도의 메모리를 요구할 수 있죠.
-   이때 **자주 쓰는 부분만 RAM에 두고**,  
    나머지는 디스크에 잠시 빼 두었다가 필요할 때 다시 가져오는 방식이 필요합니다.  
    → 이걸 가능하게 해주는 게 가상 메모리 + 페이징.

프로세스마다 “독립된 세계”가 필요해서

-   각 프로세스가 **자기만의 주소 공간(0x0000 ~ …)** 을 가지면:
    -   서로의 메모리에 막 침범하기 어렵고 (보안/안정성 ↑)
    -   프로세스가 죽어도 다른 프로세스는 안전함
-   개발자는 “이 주소 쓰면 되겠지” 하고 쓰면 되고,  
    그 주소가 실제 RAM 어딘지는 OS가 알아서 매핑.

프로그래밍 단순화

-   물리 메모리의 실제 배치, 크기, 파편화 상태를  
    **애플리케이션이 직접 신경 안 쓰게** 해 줌.
-   “메모리가 한 덩어리로 쫙 붙어있는 것처럼” 보이도록 가짜로 만들어 줌.

* * *

#### **장점**

정리해보면 가상 메모리의 장점은:

1.  **물리 메모리보다 더 큰 메모리처럼 사용 가능**
    -   디스크까지 포함해서 “논리적 메모리 크기”를 늘림.
2.  **프로세스 간 격리(Isolation)**
    -   서로의 메모리를 맘대로 접근하기 어려움 → 안정성, 보안 ↑
3.  **주소 공간 통일**
    -   각 프로세스는 항상 0부터 시작하는 자기만의 주소 공간을 가짐.
    -   라이브러리, 실행 파일을 항상 같은 가상 주소에 올리기 쉬워짐.
4.  **메모리 관리 단순화**
    -   OS 입장에서도 페이지 단위로 관리 → 할당·해제·교체가 단순

* * *

#### **단점 / 주의할 점**

1.  **오버헤드(Overhead)**
    -   주소 변환, 페이지 테이블 관리 등에 비용이 듦
    -   그래서 CPU는 TLB(Translation Lookaside Buffer) 같은 캐시를 둠.
2.  **디스크 I/O는 매우 느림**
    -   스왑이 자주 발생하면 **Thrashing(스래싱)**  
        → CPU는 거의 디스크만 쳐다보느라 바쁨 → 시스템 전체가 엄청 느려짐.
3.  **메모리 레이아웃 디버깅이 직관적이지 않을 수 있음**
    -   실제 물리 배치를 직접 보기는 어려움
    -   하지만 보통 애플리케이션 개발자는 가상 주소만 신경 쓰면 되긴 함.

* * *

#### **테스트**

mac OS 의 Command Line Tool 프로젝트 생성했습니다.

```swift
 // 1GB = 1024 * 1024 * 1024 바이트
let gigaByte = 1024 * 1024 * 1024
let size = gigaByte * 4   // 4GB 가상 메모리 시도

print("Allocating 4GB virtual memory...")

 // Int8 배열 4GB짜리 생성 (실제로는 가상 주소 공간만 크게 잡힐 수 있음)
let pointer = UnsafeMutablePointer<UInt8>.allocate(capacity: size)

 // 아직 아무 값도 안 쓰고 그냥 대기
print("Allocated. Sleeping for 20 seconds. Check Activity Monitor memory.")
sleep(20)
```

이후 활성 상태 보기를 열어서 메모리를 확인 해보니 다음과 같습니다.

![](/images/study-96/1.png)

코드상으로는 4GB 짜리 공간을 잡았지만 실제로는 메모리가 3.5MB만 사용중인 것을 볼 수 있습니다.

→ 즉, 주소는 크게 잡았지만, 실제 RAM은 다 사용하지 않고 있다.

그러면 실제로 한번 사용을 해보도록 하겠습니다.

```swift
let megaByte = 1024 * 1024
let stepMB = 100      // 한 번에 100MB씩 사용
let steps = 10        // 총 1GB까지 써보기 (100MB * 10)

// 총 1GB 만큼 할당
let totalSize = megaByte * stepMB * steps
print("Allocating \(stepMB * steps)MB buffer...")
let pointer = UnsafeMutablePointer<UInt8>.allocate(capacity: totalSize)

print("할당 완료. 이제 100MB씩 실제로 값을 써볼게요.")
print("Activity Monitor를 켜 두고, 메모리 사용량이 어떻게 변하는지 보세요.\n")

for step in 0..<steps {
    let offset = step * stepMB * megaByte
    let thisStepSize = stepMB * megaByte
    
    print("== Step \(step + 1) / \(steps): 약 \(stepMB * (step + 1))MB 사용 중 ==")
    
    // 이번 100MB 구간에 실제로 값 쓰기 → 이 시점에 페이지가 RAM에 올라감
    for i in 0..<thisStepSize {
        pointer[offset + i] = 1
    }
    
    print("Step \(step + 1) 완료. 잠깐 유지합니다. (5초)")
    sleep(5)
}

pointer.deallocate()
print("메모리 해제 완료. 프로그램 종료.")
```

메모리를 확인해보면 100MB → 200MB → 300MB … 이런 식으로 점점 올라가는 것을 확인 할 수 있습니다.

→ 즉 진짜로 접근하는 부분만 RAM에 올라오고 있습니다.

* * *

가상 주소 공간은 **약속**일 뿐, 곧바로 RAM이 아니다

-   allocate(capacity: size)로 몇 GB를 잡았다는 건,
    -   OS 입장에서 **“이 프로세스의 가상 주소 공간에서 이만큼은 얘에게 줄게”** 라는 **약속**입니다.
-   하지만 이 순간에 **실제 RAM을 전부 미리 붙이는 게 아니라**,  
    “필요하면 나중에 붙여줄게” 모드로 둡니다.
-   그래서 첫 코드에서 “allocation만 하고 안 건드렸을 때”  
    → 실제 메모리 사용량이 그렇게 높지 않았던 것.

> 요약하면  
> **“가상 주소(논리적 공간)는 크게 잡을 수 있다.  
> 그게 곧바로 ‘실제 RAM을 다 쓴다’는 뜻은 아니다.”**

실제로 접근하는 순간 → 페이지를 RAM에 할당

-   우리가 pointer\[offset + i\] = 1을 할 때마다:
    -   그 주소가 속한 “페이지(page)”를 OS가 확인하고
    -   그 페이지가 아직 RAM에 없으면:
        1.  RAM에서 빈 페이지 하나 가져오고
        2.  그 가상 페이지 ↔ 물리 페이지를 연결(매핑)하고
        3.  거기에 실제로 데이터를 씀
-   그래서 두번째 코드처럼 100MB 구간씩 실제로 값을 쓰면 → 그때그때 RAM 사용량이 올라감

> 요약하면  
> **“가상 메모리는 ‘접근하는 부분’만 실제 메모리로 바꿔 준다”**  
> 이걸 보통 **Demand Paging**이라고 부릅니다.

#### 앱 개발자가 이거 알아야하나요?

**왜 OOM(메모리 부족 크래시)이 나는지 이해할 수 있음**

iOS에서 자주 보는 상황:

-   이미지 좀 많이 띄웠더니
-   큰 배열/캐시/Realm 객체를 왕창 들고 있다가
-   갑자기 **메모리 워닝 → 앱 강제 종료**

이때 가상 메모리를 알면 이렇게 이해할 수 있어요.

-   우리 앱은 **가상 주소 공간**에서 “큰 배열, 큰 객체들”을 계속 늘리고 있음.
-   OS 입장에서는  
    → “이 앱이 실제 RAM 페이지를 계속 붙잡고 있네?”  
    → 다른 앱이나 시스템이 쓸 RAM이 모자라짐.
-   그러다 한계선을 넘으면  
    → 메모리 워닝 주고  
    → 그래도 안 줄어들면 **프로세스 kill**

> “가상 메모리 덕분에 큰 공간을 가지는 것처럼 보이긴 하지만,  
> **실제 RAM을 오래 많이 잡고 있으면 결국 죽는다**”

를 몸으로 이해하게 됩니다.

**앱 개발자가 할 일**

-   안 쓰는 객체는 참조 끊어서 **빨리 해제**되게 하기 (ARC 이해 필수)
-   큰 이미지/데이터는 **한 번에 다 들고 있지 말고, 필요할 때 로드하고 바로 버리기**
-   NSCache, 디스크 캐시(파일, CoreData, Realm 등)와 같이  
    **“RAM ↔ 디스크 사이를 잘 나눠 쓰는 구조”**로 설계하기

* * *

**“할당”과 “실제 사용”의 차이를 이해하게 됨**

우리가 아까 Swift로 테스트했을 때:

-   **큰 버퍼를 alloc만 했을 땐** 메모리가 덜 올라가고
-   **실제로 값을 써 넣을 때마다** RAM 사용이 올라갔잖아요?

이게 바로:

-   allocate(capacity:) → 가상 주소 공간만 크게 떼어놓은 상태
-   실제로 접근할 때 → 해당 페이지를 RAM에 매핑(Demand Paging)

즉, 앱에서:

> var bigArray = \[Int\](repeating: 0, count: 10\_000\_000)

이런 걸 했다고 해서 **바로 80MB가 꽉 찼다!** 가 아니고,  
실제로 그 모든 요소를 건드릴 때 메모리 사용이 늘어납니다.

그래서 개발자는:

-   “대충 넉넉하게 크게 잡을까?”를 마음대로 하면 안 되고
-   **실제로 얼마나 자주, 얼마나 넓게 접근하는지**까지 같이 생각해야 해요.
    -   예: huge 배열 전체를 매 frame마다 순회 → 캐시/페이지 미스 폭탄

이 감각이 생기면, 컬렉션 구조 설계나 데이터 접근 패턴을 훨씬 건강하게 짤 수 있어요.

* * *

**성능 튜닝: “왜 이 화면만 유독 버벅이지?”를 설명할 수 있음**

가상 메모리 + 페이징을 알면, 이런 상황을 더 잘 이해합니다:

-   스크롤만 하면 버벅이는 리스트
-   어떤 화면 들어갈 때만 갑자기 렉
-   특정 기능(필터 적용, 대량 연산)에서만 미친 듯이 느려짐

많은 경우:

-   **필요 이상으로 많은 데이터를 한꺼번에 RAM에 올려서** OS가
    -   페이지를 계속 교체하고(스왑까지 가면 더 최악)
    -   CPU는 **실제 연산보다 메모리 옮기는 데 더 많은 시간**을 쓰고 있는 중

이걸 알고 있으면:

-   Lazy 로딩(List, LazyVGrid, diffable data source 등)
-   화면에 보이는 범위만 fetch
-   CoreData/Realm도 한 번에 다 불러오지 않고 **페이징**해서 로드

같은 패턴을 “왜 이렇게 해야 하는지” 납득하고 쓸 수 있어요.

* * *

**메모리 누수(leak)가 진짜 “왜 치명적인지” 이해하게 됨**

ARC만 보면:

> “참조 카운트 안 떨어지면 객체가 안 사라진다.”

인데, 가상 메모리 관점까지 붙이면:

-   그 객체가 붙잡고 있는 페이지들도 **계속 ‘사용 중’ 상태**
-   OS는 이 페이지들을 디스크로 내보내거나 버릴 수 없음
-   결과적으로
    -   **우리 앱의 실제 RAM 점유가 계속 증가**
    -   스왑 발생 → 성능 저하
    -   끝내는 OOM → 크래시

즉, 메모리 누수는:

> “그냥 보기 안 좋은 버그”가 아니라  
> **가상 메모리 시스템 전체를 힘들게 만드는 ‘시간 폭탄’**이에요.

그래서 앱 개발자에게 강한 순환 참조, 클로저 캡처, Timer/Notification/Delegate 해제 같은 것들이  
전부 “가상 메모리 위에서의 생존 싸움”과 직결된다는 감각이 생깁니다.
